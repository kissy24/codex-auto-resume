# codex-auto-resume 設計書

2026-11-23 作成 · 初版の実装案 · 対象は macOS のローカル Codex CLI

## 1. 何を作るか

利用者が登録した Codex の会話を監視し、利用上限で作業が止まったとき、枠の回復後に同じ会話・同じ作業ディレクトリで続きを一度だけ依頼する。登録したターミナルを閉じた後も動作する。再開は会話への新しいターンの送信であり、実行途中だったシェルコマンドの復元は扱わない。

独立したリポジトリの名前を `codex-auto-resume` とする。初版は ChatGPT アカウントで認証済みの Codex CLI、macOS のログインユーザー、Python 3 の標準ライブラリ、ユーザー単位の LaunchAgent を対象とする。Codex が応答できない時間帯は OS が予約を保持する。API キーでの 429、クラウドタスク、Linux は将来の別要件とする。

**初版で最初に確かめること**は、普段使う対話型 CLI が上限で停止した後、その失敗理由を別プロセスから読み直せるかどうか。ここが成立すれば、ユーザーは普段どおり Codex を起動できる。成立しない版については、後述の代替方式を検討する。

## 2. 利用者から見た動作

対象の Codex で `/status` を開き、セッション ID をコピーする。次のコマンドは実装後の操作例。上限到達の前後いずれでも登録できる。

```sh
codex-auto-resume watch <session-id>
codex-auto-resume status <session-id>
codex-auto-resume cancel <session-id>
```

- `watch` は対象の会話と作業ディレクトリを検証し、次の上限停止に対する予約を一つ作る。同じ会話を再登録した場合は既存予約の状態を表示する。複数の利用枠がある場合は `--bucket <limit-id>` で使用する枠を指定できる。
- `status` は監視中、回復待ち、再開中、終了、要確認の区別を示す。待機中は対象の利用枠、次回確認の現地時刻、直近の失敗理由が分かる。終了後にも結果を確認できる。
- `cancel` は送信前の予約を解除する。送信済みなら、その事実を表示する。すでに起動した Codex の作業を強制終了する操作は初版の対象外とする。
- たとえば短時間枠が 14:00、週間枠が翌日 09:00 に回復し、両方を使い切っている場合、再確認は翌日 09:00 以降になる。Mac がその時刻にスリープ中なら、復帰してジョブが動ける時点で再確認する。ログアウト中は次回ログイン後に確認する。

## 3. 監視と再開の流れ

| 段階 | 実装する処理 |
| --- | --- |
| 登録 | セッション UUID を検証する。Codex App Server の `thread/read` で会話と作業ディレクトリを取得する。Codex と監視ツールの実行パスを解決して保存し、LaunchAgent を登録する。 |
| 停止の検知 | `thread/turns/list` で最新の 1 ターンを取得する。状態が `failed` で `error.codexErrorInfo` が `usageLimitExceeded` の場合に、失敗ターン ID を保存する。通常終了、ユーザーによる中断、通信エラーで再開を予約しない。 |
| 回復待ち | `account/rateLimits/read` で対象の `limitId` の `primary` と `secondary` を読む。使用率が 100% 以上の窓が複数あれば、既知の `resetsAt` のうち最も遅い時刻を使う。タイムスタンプは Unix 秒で保存する。 |
| 再確認 | 予定時刻を過ぎたら利用枠を再取得する。対象枠を特定でき、上限状態が解けたことを確認したときだけ次へ進む。最新ターン ID が変わっていれば手動再開済みとして予約を解除する。 |
| 再開 | 送信を試みる事実をディスクに記録し、保存した作業ディレクトリから `codex exec resume <session-id> <prompt>` を実行する。終了コードと結果を記録し、定期監視を終了する。 |

再開メッセージは「利用上限で中断した依頼について、現在の作業状況と実行済みの操作を確認し、元の依頼の範囲で未完了の作業を続けてください。」とする。セッション指定には UUID を使用する。Codex のサンドボックス、承認、プロジェクト信頼の設定を上書きするフラグは渡さない。対話的な承認が必要な作業は利用者が会話を開いて引き継ぐ。

照会には `codex app-server --stdio` を使い、`initialize`、`initialized` の後にリクエストを送る。RPC の応答はリクエスト ID で対応付け、タイムアウトを設ける。最新ターンの取得には `limit=1`、`sortDirection=desc`、`itemsView=notLoaded` を指定する。会話の本文は保存しない。[Codex App Server 公式仕様](https://developers.openai.com/codex/app-server) · [Codex CLI 公式リファレンス](https://developers.openai.com/codex/cli/reference/)

## 4. 予約の状態と例外処理

| 状態 | 次の動作 |
| --- | --- |
| `watching` | 約 60 秒間隔で最新ターンを確認する。通常の成功ターンの後も、予約を消費するまで監視する。 |
| `waiting` | 失敗ターンと次回確認時刻を保存済み。期限前の起動はローカル判定で終了する。期限後に利用枠と会話を再確認する。 |
| `dispatching` | CLI 起動直前に永続化する。異常終了すると送信の成否が曖昧になるため、自動で再送せず `needs_attention` として履歴確認を促す。 |
| `done` | 再開用 CLI が正常終了した状態。元の依頼の達成可否は会話で確認できる。 |
| `cancelled` | 予約が手動で解除された、または対象の失敗ターンより後に利用者が会話を進めた状態。 |
| `needs_attention` | 原因と確認先を表示し、自動再開を止める。確認後は明示的に新しい予約を作れる。 |

一時的なネットワーク障害や RPC タイムアウトでは予約を保持し、再照会の間隔を 1、2、4 分と延ばし、最大 15 分とする。枠のリセット時刻だけが欠けている場合も間隔を空けて利用率を再取得する。認証切れ、利用枠の特定不能、支出上限、作業ディレクトリ消失、再開用 CLI の異常終了は `needs_attention` にする。支払い・クレジット消費は行わない。

**二重送信をどこまで防げるか。** 同じセッションの登録、解除、送信直前の状態更新を同じファイルロックで直列化する。監視プロセスを二重起動しても送信権を得られるのは一つだけにする。送信成否が不明な予約は再送しないため、クラッシュ時には手動確認が必要になる。また、別端末の Codex による手動送信はこのロックを取得しない。直前の最新ターン再確認から CLI 起動までのわずかな競合は残る。

## 5. 配置と運用

| 保存先 | 内容 |
| --- | --- |
| `~/.local/bin/codex-auto-resume` | 利用者が呼ぶ CLI。LaunchAgent にも恒久配置した実行パスを渡す。 |
| `~/Library/LaunchAgents/local.codex-auto-resume.<uuid>.plist` | ログイン時と約 60 秒ごとの起動設定。セッション単位で登録・解除する。 |
| `~/Library/Application Support/codex-auto-resume/<uuid>/` | `state.json`、ロック、診断ログ。ディレクトリは所有者限定、ファイルは原則 0600 とする。 |

状態にはスキーマ版、セッション ID、作業ディレクトリ、Codex 実行パス、利用枠 ID、状態、失敗ターン ID、次回確認時刻、最終結果を保存する。状態ファイルは同一ディレクトリの一時ファイルから原子的に置換する。診断ログは日時・状態遷移・終了コードを中心とし、認証情報、会話本文、CLI の全出力を常時保存しない。

登録途中の失敗では作成済みの予約と plist を整合させ、再登録で復旧できるようにする。終端状態では次回ログイン時の再登録も解除し、結果だけを残す。再開中の `cancel` が実行中の CLI を巻き込まないよう、状態判定を先に行う。アンインストール手順には、有効な予約の解除、実行ファイル削除、利用者が希望した場合の履歴削除を記載する。

## 6. リポジトリ構成と実装順

```text
README.md                       導入・登録・解除・状態別の対処
docs/design.md                  この設計書
bin/codex-auto-resume           CLI と監視処理の入口
tests/                          状態遷移、模擬 RPC、launchd 登録のテスト
.github/workflows/test.yml      macOS 上の自動テスト
```

1. **実機で検知経路を確定する。** 自然に上限へ達した対話型セッションで、最新の失敗ターン ID とエラー種別が別プロセスから読み直せるか、対象の利用枠を一意に対応付けられるかを確認する。失敗理由が履歴に残らない場合は、その CLI 版では既存セッション監視を対応済みにしない。代替案は、ツール経由で開始したセッションに対象を絞り、実行中の App Server 通知を購読する方式とする。
2. **試作を移植する。** 一時ディレクトリにある単一ファイルの Python 試作を起点に、まず既存の模擬テストを再現する。続いて予約の競合、登録失敗からの復旧、終了後の LaunchAgent 解除、ログ最小化を実装する。
3. **利用手順と配布を仕上げる。** クリーンなユーザー環境でインストールから解除まで確認する。README に検証した macOS、Python、Codex CLI の版、対応する認証方式を明記する。CI は模擬 RPC で完結させ、実アカウントでの確認結果は別に記録する。

## 7. 受け入れ条件

| 場面 | 合格条件 |
| --- | --- |
| いずれかの枠が未回復 | リセット予定時刻を過ぎても、再照会で未回復なら Codex を起動しない。 |
| 回復後に別の会話が開かれている | 登録した UUID と元の作業ディレクトリで一度だけ新しいターンが始まる。 |
| 手動再開・解除・監視の二重起動 | 送信前に観測した手動再開や解除を尊重する。並行する監視処理からの二重送信がない。 |
| プロセス異常終了・認証切れ | 予約の結果と次に利用者が確認すべきことが `status` で分かる。送信成否が不明な予約を再送しない。 |
| スリープ・再ログイン | 期限を過ぎた予約を復帰後に再評価する。終了したジョブが再ログインで復活しない。 |
| 登録失敗・再登録・後片付け | 登録を再試行できる。終了後も結果を読めて、不要な LaunchAgent が残らない。 |

**確認済みの範囲。** 試作では Codex CLI 0.171.0 の App Server 接続とセッション UUID 指定の再開構文を確認した。模擬サーバーでは、通常ターン、二つの利用枠の回復待ち、手動再開による取り消し、回復後の一回送信、クレジット枯渇時の停止を確認した。

**初版公開前に残る実機確認。** 実アカウントでの上限到達から再開までの一連の動作、元の CLI と非対話再開での承認設定の扱い、ログインユーザーの LaunchAgent 登録、スリープと再ログインをまたぐ動作。模擬テストの成功と区別して記録する。
